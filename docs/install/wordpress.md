# WordPress からの移行

WordPress のサイトの記事・固定ページ・カテゴリ・タグ・画像を Pagewright に取り込み、サイトを切り替えるまでの流れです。
取り込みは、WordPress の「ツール → エクスポート」で書き出したファイル（WXR。「[用語集](./glossary.md)」）を使います。

## 全体の流れ

1. 今の WordPress のサイトは動かしたまま、Pagewright を別の名前で入れて試す
2. WordPress から書き出す
3. 試しに取り込んで（`--dry-run`）、確かめる
4. 取り込む
5. 公開サイトを見て、直す
6. ドメインを切り替える

## 移るもの・移らないもの

| 移るもの | 移らないもの |
| --- | --- |
| 記事（WordPress の「投稿」）と固定ページ。本文、公開日、親ページ | コメント（Pagewright にコメント機能はありません） |
| カテゴリ（親子も）とタグ | メニュー（管理画面の「サイトの設定」で作り直します） |
| 画像（`--download-media` を付けたとき） | アイキャッチ画像 |
| 記事の番号（WordPress の投稿 ID）と URL。`/?p=123` のような古い URL からも転送します | 投稿者（すべて、取り込みのときに指定した1人になります） |
| 予約投稿（予約日時が先のもの） | 「投稿」「固定ページ」以外の種類（カスタム投稿タイプ）、画像以外の添付ファイル（本文のリンクは元の URL のまま）、ゴミ箱の中のもの、自動保存 |

- **変換できない部分**（ショートコード、`<script>` など）は、本文の中に「カスタムHTML」の枠として残します。公開サイトには、安全なタグだけにして出します。あとで管理者が直します（下の「5. 公開サイトを見て、直す」）
- **カスタムフィールド**（ACF の値など）はデータとして残しますが、いまは管理画面にも公開サイトにも出ません

### 記事の状態

| WordPress での状態 | 取り込んだあと |
| --- | --- |
| 公開済み | 公開 |
| 予約済み（日時が先） | 予約（その日時に公開されます） |
| 予約済み（日時が過ぎている）、非公開、レビュー待ち、パスワード保護 | 下書き（勝手に公開されないように） |
| 下書き | 下書き |
| ゴミ箱、自動保存 | 取り込みません |

## 1. Pagewright を別の名前で入れて試す

今の WordPress のサイト（例：`www.example.co.jp`）は、切り替えるまでそのまま動かしておきます。
Pagewright は、「[導入](./setup.md)」の手順で入れます。そのとき、公開サイトのドメイン（`.env` の `PAGEWRIGHT_SITE_DOMAIN`）は、試しのあいだ別の名前（例：`new.example.co.jp`）にしておきます。DNS もその名前で設定します。

取り込みには、次の2つを使います。

- **サイトのID**：手順5の `init` で表示されたもの。`.env` の `PAGEWRIGHT_SITE_ID` にも書いてあります（`grep PAGEWRIGHT_SITE_ID .env`）
- **作成者のメールアドレス**：取り込んだ記事の作成者にする人。そのサイトのメンバー（`init` で作った管理者など）にします

## 2. WordPress から書き出す

1. WordPress の管理画面で「ツール」→「エクスポート」を開きます
2. 「すべてのコンテンツ」を選んで、「エクスポートファイルをダウンロード」を押します
3. ダウンロードしたファイル（`.xml`）を、Pagewright のサーバーの `/opt/pagewright/deploy/export.xml` に置きます（`scp` などで）

`cli` はユーザーID 10001 で動くので、ファイルをだれでも読めるようにしておきます。

```sh
cd /opt/pagewright/deploy
chmod 644 export.xml
```

## 3. 試しに取り込む（`--dry-run`）

`<サイトのID>` と `you@example.co.jp` を置き換えて実行します。`--dry-run` を付けると、データベースには何も書き込まずに、取り込んだらどうなるかを表示します。

```sh
docker compose run --rm -v "$PWD/export.xml:/import/export.xml:ro" cli \
  import-wxr --site <サイトのID> --author-email you@example.co.jp --download-media --dry-run /import/export.xml
```

| 指定 | 意味 |
| --- | --- |
| `-v "$PWD/export.xml:/import/export.xml:ro"` | サーバーの `export.xml` を、`cli` の中から `/import/export.xml` として読めるようにする |
| `--site` | 取り込む先のサイトのID |
| `--author-email` | 作成者にする人のメールアドレス |
| `--download-media` | 画像を今の WordPress のサイトからダウンロードして、Pagewright に保存する。本文の画像も、保存した画像を指すように書き換える。**今の WordPress のサイトに、サーバーからインターネットを通して接続できる必要があります**（付けないと、本文の画像は元のサイトの URL のままになり、元のサイトを止めると表示されなくなります） |
| `--dry-run` | 試しに取り込む（データベースに書き込まない）。`--download-media` を付けていれば、画像のダウンロードも試します |
| `--media-root` | 画像の保存先。Docker の構成では初期値（`/data/media`）のままでよいので、付けなくてかまいません |
| `--pagewright-urls` | WordPress の URL（`/2024/05/opening/` など）を使わず、Pagewright の URL（`/posts/…/`）にする。古い URL からは自動で転送します。付けなければ、WordPress の URL をそのまま使います |

表示はたとえば次のようになります。

```

サイト：やまだ商店（https://example.jp）

固定ページ：新規 3、取り込み済み 0、対象外 0、失敗 0

タグ：新規 2、既存 0、対象外 0、失敗 0
画像：新規 0、既存 0、対象外 0、失敗 0

[記事 101] 開店のお知らせ　/2024/05/開店のお知らせ/

  - 画像に代替テキストがないため、仮に「bread_photo」としました。内容に合わせて直してください
      元の内容：<img src="https://cdn.example.net/images/bread_photo.png"/>

- 作成者はすべて指定したユーザーにしました（WordPress の投稿者は引き継いでいません）
```

（Pagewright のテスト用の見本のファイルで試した結果を、一部省いたものです。）

「■ 確認が必要なもの」の `[記事 101]` は WordPress での番号、その後ろはタイトルと公開サイトでの URL です。あとで直すときに使うので、表示を保存しておくと便利です。

```sh
docker compose run --rm -v "$PWD/export.xml:/import/export.xml:ro" cli \
  import-wxr --site <サイトのID> --author-email you@example.co.jp --download-media --dry-run /import/export.xml > import-check.txt
```

## 4. 取り込む

問題がなければ、`--dry-run` を外して実行します。

```sh
docker compose run --rm -v "$PWD/export.xml:/import/export.xml:ro" cli \
  import-wxr --site <サイトのID> --author-email you@example.co.jp --download-media /import/export.xml
```

取り込みが終わると、公開サイトが自動で書き出されます。予約投稿は、その日時に公開されます。

**同じファイルを、もう一度取り込んでもかまいません。** すでに取り込んだもの（同じ番号の記事・固定ページ、同じ URL（英数字）のカテゴリ・タグ、同じ画像）は「取り込み済み」「既存」として、**変えずに**そのままにします。新しいものだけが足されます。
そのため、取り込んだあとに WordPress で書き直した記事は、取り込み直しても Pagewright には反映されません。取り込んだあとは、WordPress では記事を書き直さないようにするか、Pagewright の管理画面で同じように直します。

## 5. 公開サイトを見て、直す

1. 試しの名前（例：`https://new.example.co.jp/`）で公開サイトを開き、記事や固定ページを見て回ります
2. 「確認が必要なもの」に出た記事や固定ページを、管理画面で開きます。記事の一覧の「タイトルやURLで探す」に、タイトルか URL を入れると見つかります
3. 本文の「カスタムHTML」の枠（元のサイトの HTML をそのまま残したもの）は、管理画面では中身を直せません。消すか（管理者だけ）、そのままにします。ショートコードで作っていたお問い合わせフォームなどは、枠を消して、ツールバーで Pagewright の部品を入れ直します（「[本文の書き方](../guide/editor.md)」）
4. 仮の代替テキストが付いた画像は、本文から消して、正しい説明を付けて入れ直します（「[画像](../guide/images.md)」）
5. メニュー、ロゴ、トップに載せる固定ページなどを「[サイトの設定](../guide/settings.md)」で決めます

## 6. ドメインを切り替える

1. WordPress で記事を書くのをやめてもらいます（切り替えのあとに書いたものは移りません）
2. `.env` の `PAGEWRIGHT_SITE_DOMAIN` を本番の名前（例：`www.example.co.jp`）に書き換え、`docker compose up -d` を実行します
3. DNS で、`www.example.co.jp` の A レコード（と AAAA レコード）を、Pagewright のサーバーに向け直します。反映されると、Caddy が自動で証明書を取ります（「[導入](./setup.md)」の手順3・4）
4. 反映されたら、管理画面の「ホーム」の「サイトを更新」を押して、公開サイトを新しいドメインで作り直します
5. `https://www.example.co.jp/` を開いて、表示と、古い URL（WordPress のときのページの URL）から開けるかを確かめます
6. 問題がなければ、WordPress のサイトを止めます。`--download-media` を付けずに取り込んだときは、本文の画像が元のサイトを指しています。取り込み直しても取り込み済みの記事は変わらないので、止める前に、管理画面で画像を入れ直してください

試しの名前（`new.example.co.jp`）は、切り替えたあとは使わないので、DNS から消してかまいません。
