# Pagewright 設計ドキュメント

## 概要

Pagewrightは、中小企業や個人のWebサイト向けの、セルフホストでも速く、日本語に強いCMSです。管理画面は動的に動き、公開サイトは静的なファイルとして書き出すので、どのCDNやWebサーバーでも速く配信できます。

- **提供形態：** セルフホスト版（OSS）と、こちらで運用するSaaS版の2つ。
- **最初のユーザー：** 中小企業・個人のサイト。WordPressからの乗り換えを主な入口と考える。
- **位置づけ：** どこのサーバーでも同じように動く、WordPressの代わりになる選択肢。
- **名前の由来：** page＋wright（shipwrightなどの「職人」）。ページを丁寧に作る職人の道具、という意味の造語。

## 基本方針

差別化の軸は「セルフホストを主役にする」と「日本向けに作り込む」の2本です。普通のサーバーでも、SaaS版と同じ品質で全機能が動くことを前提に設計します。

### 柱1：セルフホストが主役

- Goのバイナリ1つ＋PostgreSQLで全機能が動く。Docker ComposeでPostgreSQLごと同梱する
- SaaS版とセルフホスト版は同じコードで動く
- 予約投稿やジョブはDBに永続化し、再起動しても取りこぼさない
- バックアップ／復元、アップデート、ヘルスチェックを標準で備える
- 公開サイトは静的なので、管理サーバーが落ちても表示され続ける
- 主要なVPSやクラウド向けのワンクリック導入テンプレートを用意する
- レンタルサーバー（共用サーバー）には対応しない。公開サイトをSFTPで送る方式も取らない（現代的な配信先ではないため）

### 柱2：日本向けに作り込む

- 日本語の全文検索（公開サイトはPagefind）
- ルビ、縦書き、和暦、日本の祝日
- JIS X 8341-3に準拠したアクセシビリティ
- 非エンジニアが迷わない日本語の管理画面

## 決定事項

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 名前 | Pagewright（ページライト） | 意味がすぐ伝わり、日本語の発音でも崩れない |
| 最初のユーザー | 中小企業・個人のサイト | セルフホストと日本語対応の両方が刺さる層。運用は1〜2人が多い |
| ライセンス | 本体はAGPLv3、テーマ・プラグインSDKはMIT（予定） | クローズドな競合SaaSを作らせない。テーマ制作者には制約をかけない |
| 言語・ランタイム | Go（本体）＋TypeScript（管理画面） | シングルバイナリ、少ないメモリ、速い静的生成、wazeroによるWasm実行 |
| 管理画面 | React＋Vite。ビルドしたファイルをGoのバイナリに埋め込む | Tiptapの対応が最も厚い |
| テーマ | Goのテンプレート。Astroには依存しない | HTMLとCSSが書ければ扱える |
| 本文の保存形式 | ProseMirror（Tiptap）のJSONにスキーマのバージョン番号を付けて保存。移行元の本文の原文も残す。Markdownの書き出し・取り込みに対応 | エディタとの変換を2方向で保守しなくて済む。移行で変換しきれなかった部分を後から直せる |
| エディタ | Tiptap | ProseMirrorの土台。IME・ルビ・縦書きプレビューを最初に検証する |
| テナンシー | 本体をマルチテナント対応にする | SaaSの原価を下げる。セルフホストでも複数サイトを同じ仕組みで扱える |
| データ分離 | 共有PostgreSQL＋テナントID列＋Row Level Security | アプリにバグがあってもDB側で他テナントを見せない |
| ユーザー | ユーザーは全テナント共通。所属と役割（管理者・編集者）はテナントごとに持つ | 制作会社のように1人で複数サイトを扱える。パスキーは人にひもづく |
| DB | PostgreSQL 18のみ（セルフホストも）。拡張機能は使わず、標準のイメージで動かす | 2種類のDBを保守しない。手軽さはDocker Composeで補う。18は修正版が重なっていて安定し、サポート期間も長い |
| 日本語検索 | 公開サイトはPagefind（ビルド時に索引を作り、ブラウザで検索）。管理画面は部分一致（ILIKE） | 公開サイトを静的なまま検索できる。pg_bigmは独自イメージの保守とPostgreSQLの更新ごとの作り直しが重い。1万件なら部分一致で足りる |
| サイト規模 | 〜1万ページ、記事1本の更新は数秒で反映 | 毎回の全体ビルドで届く範囲 |
| ビルド | 毎回全体を作り、前回の出力と中身を比べて変わったファイルだけ配置する。ページ間の依存関係は管理しない | 「新着記事」などの欄でほぼ全ページが影響を受け、差分ビルドの効果が小さい。時間がかかるのは描画より配置とCDNのパージ |
| 公開中の版と編集中の版 | 本文などは保存のたびに版（リビジョン）として残し、コンテンツは公開中の版と予約中の版を指す | 公開済みの記事を編集しても、書きかけが次のビルドで公開されない。公開済み記事の予約更新ができる |
| URLの管理 | 公開URL・旧URL・リダイレクトをテナントごとに一意な1つの表で管理する | 記事・固定ページ・カテゴリのURLの衝突をDBで防ぐ。移行で最重要の「URLの維持」を1か所で保証する |
| 権限・承認 | MVPは管理者・編集者の2役（テナントごと）＋ログイン不要の期限付きプレビューリンク | 承認フローは後から追加できる |

## アーキテクチャ

管理は動的、公開は静的という構成です。

```
[管理画面(TypeScript+Tiptap)] → [Go本体: API・認証 / ジョブキュー・ビルド / Wasmプラグイン] ⇄ [PostgreSQL: テナントID+RLS]
                                        │ 書き出し
                                        ▼
                              [静的ファイル: HTML・画像・検索索引] → [配信: nginx / CDN] → 閲覧者
```

- **管理画面とAPI：** 動的。VPNや社内ネットワークの内側に置ける
- **ジョブキュー：** 予約投稿は「予約ビルド」としてDBに永続化。ビルドはテナントごとに順番待ち
- **ビルド：** 毎回全体を作り直す。前回の出力と中身（ハッシュ）を比べ、変わったファイルだけを配置する。ページ間の依存関係は持たない
- **配信：** 出力先はローカル（nginx）かS3互換ストレージ。変わったパスだけCDNでパージ
- **マルチテナント：** 全テーブルにテナントIDを持たせRLSを有効化。リクエストごとにDBセッションへテナントIDをセット
- **動的な部分：** フォーム送信やプレビューは小さなAPIとして切り出す

## 移行機能

各CMSから共通の中間形式に変換して取り込む。中間形式はテナント単位の書き出し・取り込みにも使う。

優先順位：1. WordPress（WXRとREST API） 2. Markdown系・Ghost・EmDash 3. Movable Type 4. 自治体向けCMS

- **URLの維持：** 旧URLのまま出力するか、リダイレクトを自動生成（最重要）
- **本文の変換：** ショートコード、Gutenbergブロック、ACFを本文のJSONへ。移行元の原文はそのまま残し、変換しきれなかった部分を後から直せるようにする
- **メディア：** ダウンロードしてパスを書き換える
- **ドライラン：** 変換できなかったものの一覧を先に見せる

## プラグイン

MVPではAPIを公開しない。

- **コア機能：** SEO、サイトマップ、リダイレクト、画像最適化、フォーム
- **ビルド時プラグイン：** カスタムブロック、フィールド型、本文変換（管理側だけで動く）
- **実行時プラグイン：** フォーム送信先、Webhook、外部連携。Wasm（wazero）で隔離し権限を宣言させる
- **開放の進め方：** コア機能を内部的にフックで作り、形が固まってから外部に開放する

## フォーム

MVPは問い合わせフォーム1種類の固定版（通知メール・自動返信メール・スパム対策つき）。以下の、管理画面からコードなしで作れるフォームはv1。

- 入力欄：テキスト、メール、電話、選択肢、チェック、日付、ファイル添付。必須・形式チェック、確認画面、完了ページ
- 日本向け：ふりがな、郵便番号からの住所補完、全角・半角の自動変換、個人情報の同意チェック
- 送信先はGo本体の小さなAPI。内容はテナントごとにDBへ保存し、一覧表示・CSV書き出し
- 通知メールと自動返信メール
- スパム対策：ハニーポット、送信間隔チェック、レート制限。外部CAPTCHAは任意
- 個人情報の保存期間を設定し自動削除
- 外部連携は実行時プラグイン（Webhook）

| テーマ | 想定 | 主な部品 | 時期 |
| --- | --- | --- | --- |
| ブログ | 個人ブログ、オウンドメディア | 記事一覧、タグ、著者、関連記事 | v1 |

- テーマはGoのテンプレート。標準テーマもMITで配布

## 実装設計

### データモデル

- すべてのコンテンツを「種類＋共通の項目（タイトル、URL、本文、状態、公開日時、著者など）＋JSONの追加項目」で持つ
- タイトル・本文・追加項目は版（リビジョン）として保存のたびに残す。最新の版が編集中の内容。コンテンツは「公開中の版」と「予約中の版（と公開日時）」を指し、状態（下書き・予約・公開）はそこから決まる。ビルドは公開中の版だけを読む
- 公開URL・旧URL・リダイレクトは1つの表（routes）で持ち、パスはテナント内で一意。日本語のパスはデコードしてNFCに正規化してから保存する。`/?p=123` のようなクエリ付きのURLは静的ファイルでは出せないので、リダイレクトとして扱う
- MVPで見せる種類は記事と固定ページ
- 分類はカテゴリ（階層あり）とタグ
- メディアはテナントごとに管理し、実体はオブジェクトストレージ
- ACFなどの追加項目はJSONの追加項目にそのまま取り込む
- 将来、メニューやスタッフ紹介などの種類をDBを作り直さずに追加できる
- コンテンツは内部IDとは別に、URL用の番号をテナントごとの連番で持つ（`/posts/123/` の `123`）。WordPressの記事IDをそのまま引き継いで、IDを使ったURLを維持するため
- テナント分離の例外：ユーザーの表だけはテナントIDを持たない。RLSで「現在のテナントに所属しているユーザー」だけを見せる。ログインのときにメールアドレスからユーザーを探す処理は、用途を絞ったDB関数1つだけに限る

### 本文JSONのスキーマ

- ブロック：段落、見出し（h2〜h4）、リスト、画像（代替テキスト必須）、引用、表、区切り線、ボタン、埋め込み（YouTube、Googleマップ）、フォームの差し込み、カスタムHTML
- 文字装飾：太字、斜体、リンク、ルビ、インラインコードだけ（色・サイズはテーマで決める）
- カスタムHTML：移行の受け皿。管理者だけが使え、出力時にサニタイズ
- 形式はProseMirror（Tiptap）のJSON。スキーマのバージョン番号を持たせ、古いデータを自動変換
- 段組みはv1

### URLの設計

| 対象 | URL |
| --- | --- |
| 記事 | 初期値は `/posts/{URL}/`。`/posts/{年}/{月}/{URL}/` なども選べる。`posts` はサイトごとに変更可（`news` など） |
| 固定ページ | `/{URL}/`。階層も持てる |
| カテゴリ | `/posts/category/{URL}/` |
| タグ | `/posts/tag/{URL}/` |

- URL欄は最初は見せない。未入力なら記事IDで決まる（`/posts/123/`）。「詳細設定」で編集
- 欄の名前は「ページのURL（英数字）」。英小文字・数字・ハイフンのみ。日本語が入力されたらその場で案内
- 固定ページはテーマで初期値を用意（会社概要→`/company/` など）
- 英語のURL候補の自動提案はv1
- WordPressから移行した日本語URLはそのまま受け入れる
- 旧URLはroutesにリダイレクトとして持ち、CDNルールやnginx設定として書き出す。URL変更時もリダイレクトを残す
- 番号だけのURL（`/posts/123/`）と衝突しないよう、数字だけの「ページのURL」は使えない

### リポジトリと開発の進め方

| 領域 | 使うもの |
| --- | --- |
| バージョン管理・タスク | mise（`mise run dev`、`test`、`gen` など） |
| Go本体 | slog、pgx＋sqlc、goose、River（ジョブキュー）、wazero |
| Goのテストと検査 | testing＋go-cmp、golangci-lint、govulncheck |
| 管理画面 | pnpm、React＋Vite＋TanStack Router、TanStack Query、Tailwind CSS＋shadcn/ui、React Hook Form＋Zod、lucide-react、Tiptap |
| 管理画面のテストと検査 | Biome、Vitest、Playwright＋@axe-core/playwright |
| DBの周辺 | Squawk、tbls、pgBackRest（自分たちが運用する環境） |
| 開発環境 | Docker Compose（PostgreSQL、Mailpit） |
| Gitと依存関係 | lefthook、Renovate |
| CIと配布 | GitHub Actions（認証はOIDC）、GoReleaser（amd64・arm64、GHCR） |

- テナント分離のテストが最優先。APIのすべての入口で、本物のPostgreSQLに対して自動テスト
- RLSとマイグレーションの変更は必ず人がレビュー
- トランクベースで小さなPRを積む

### DBへの接続

- アプリは専用ユーザー `pagewright_app` で直接ログインする。スーパーユーザーやテーブルの所有者では接続しない。接続後に `SET ROLE pagewright_app` でも切り替え、二重に守る
- マイグレーションはテーブルの所有者のユーザーで実行する。所有者はRLSの対象外なので、データ移行は全テナントに対して行える
- `pagewright_app` へのパスワード設定（`ALTER ROLE pagewright_app LOGIN PASSWORD ...`）は導入手順に含める

### 認証

- パスワードは使わない。ログインはメールのログインリンクとパスキーだけ
- パスキーは実績あるライブラリ（go-webauthnなど）。セッションはHTTP-onlyのCookie

### セルフホスト版のバックアップ

- 本体に組み込む。毎日 `pg_dump` とメディアをS3互換ストレージかローカルへ
- 復元はCLIで行う（管理画面からの復元はv1）

## MVPの範囲

入れるもの：

- 記事と固定ページの作成・編集（Tiptap、ルビ対応）
- 下書き・予約・公開の3状態と期限付きプレビューリンク
- 管理者・編集者の2役
- 静的出力（全体ビルド＋変わったファイルだけ配置）と、nginx・S3互換ストレージへの配置
- 日本語の全文検索（Pagefind）
- SEO、サイトマップ、RSS、リダイレクト
- 問い合わせフォーム1種類の固定版（通知・自動返信メールつき）
- 標準テーマ1種（コーポレート）と、ロゴ・配色の設定
- WordPressからの移行（WXR）
- テナントID＋RLSを前提にしたデータモデル

作る順番：最初に「実在するWordPressサイト1つをWXRから移行し、同じURLで公開する」までを縦に通し、機能はその上に足す。

後回し：管理画面で作るフォーム、ブログテーマ、管理画面からの復元、プラグインAPIの公開、承認フロー、縦書きテーマ、WordPress以外の移行、SaaSの申込・課金。

残っていること：

- [ ] 作りながら決める：画像の処理、監視とログ
